# Bluetooth diagnostic protocol

This implementation is a source-derived hypothesis, not a hardware-validated port. Native XCTest runs in the macOS GitHub Actions workflow. The first real tag connection remains pending. It does not activate UWB, ring, reset, rebind or write tag settings.

The supplied SmartThings APK analysis found encryption service `eedd5e73-6aa8-4673-8219-398a489da87c`, nonce characteristic `a12be31c-5b38-4773-9b9d-3d5735233a7c`, and encrypted proof characteristic `4ebe81f6-b952-465e-9ece-5ca39d4e8955`. These identifiers and the key derivation need hardware confirmation. The master secret is the authorized owner's normalized 16-byte `bleD2D.encryptionKey`. Accepted cipher descriptors are `AES/CBC/PKCS5Padding`, `AES/CBC/PKCS7Padding`, `AES-CBC-PKCS5Padding`, `AES-CBC-PKCS7Padding`, `AES_128-CBC-PKCS5Padding` and `AES_128-CBC-PKCS7Padding`, matched case-insensitively. Each stores the explicit canonical transform `AES/CBC/PKCS7Padding`; Java PKCS5Padding for AES is interoperable with CommonCrypto PKCS7 padding. Other modes, key sizes and malformed descriptors fail closed.

Derive `Kauth = SHA256(master || 00 00 00 01 || UTF8(bleAuthentication))[0..<16]`. Subscribe sequentially to NONCE and ENCRYPTED_NONCE, waiting for subscription callbacks, then write a secure random 16-byte phone nonce. Wait for its write acknowledgement and the tag's 16-byte nonce before sending AES-CBC(Kauth, IV=tag nonce, plaintext=`smartthings`). Verify the tag's encrypted proof using IV=phone nonce. The current implementation requires the exact 11-byte plaintext after padding removal; it deliberately fails closed if the real device adds undocumented bytes. A wrong proof disconnects immediately. A successful proof and write acknowledgement are both required before battery read.

Derive the command key with the same KDF and the tag nonce as context. Read `DEE30004-182D-5496-B1AD-14F216324184` in service FD5A. Decrypt with command key and IV=tag nonce. Parse four little-endian counter bytes, then exactly one battery byte: 00 very low, 01 low, 02 sufficient, 03 full. These are discrete levels, not percentages. The counter utility rejects repeated or decreasing counters; this diagnostic performs a single battery read per session.

The battery characteristic and level mapping are cross-referenced by [uTag ConnectedTagConnection](https://github.com/KieronQuinn/uTag/blob/f46375a9c2af6de4c8678f6aba7b91972054ae74/app/src/main/java/com/kieronquinn/app/utag/components/bluetooth/ConnectedTagConnection.kt). Source analysis suggests another control-indication subscription after authentication, but its exact UUID/configuration has not been established here. This diagnostic attempts the direct GATT battery read without inventing that step. If firmware requires it, the read will fail or time out; that failure is evidence to investigate, not a battery result.

iOS exposes peripheral UUIDs, not Android Bluetooth MAC addresses. Discovery filters Samsung manufacturer ID 0x0075 or FD5A service advertisements and requires explicit selection. This may include unrelated Samsung hardware or omit a tag whose advertising format differs. No advertised name proves ownership; the cryptographic exchange must succeed. A Galaxy may hold the active connection: disconnect it before an owner-run test. Every active phase times out, errors disconnect, and logs never contain secrets, tokens, nonces, ciphertext or device IDs.

Tests were authored before production code. The production handshake reducer is exercised for both nonce and proof arrival orders, early/duplicate events, and cancellation. It emits proof and battery actions once; the CoreBluetooth driver uses those actions rather than maintaining a separate ordering oracle. Timeout and disconnect cancel that state; delegate callbacks from a cleared peripheral are ignored. CoreBluetooth callback integration still requires hardware checks. KDF expected values were independently computed using Python hashlib, and the first AES-CBC block uses the NIST SP 800-38A vector. Native RED/GREEN checks run on macOS Actions; the Windows authoring host has no Swift/Xcode runner. CoreBluetooth hardware behavior remains unverified. The owner has confirmed Samsung login and tag listing; the build host performs no live owner-account or tag requests.

Samsung descriptor evidence comes from the supplied APK's `classes8.dex` (SHA256 `582aa601197129d9489b0db9d55c493603e9544c17b7910d10d926a3aa693623`): `tf0.b` constructor at code item `0x6460cc` normalizes dash/underscore descriptors into a Java transform, and `tag.gatt.internal.x` constructor at `0x4c005c` supplies `AES-CBC-PKCS7Padding`. The same DEX contains `AES_128-CBC-PKCS7Padding` at string index 8835. This implementation accepts only the explicit equivalents listed above; it does not reproduce Samsung's permissive defaults for missing tokens. The owner's actual cipher value has not been observed. The counter/payload-length checks are deliberately stricter than the recovered APK's four-byte stripping: unexpected firmware frames fail instead of being interpreted speculatively.
